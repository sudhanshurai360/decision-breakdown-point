# Reproducing the results

**One rule:** *predictions in, everything else out.* Every scoring / identification / fragility /
decision result in the paper is CPU-deterministic (seeded) and regenerates from one command. The
**only** thing that is NOT regenerated on a normal machine is the **neural-net predictions**
(nbeats / nhits / tft / itransformer / dlinear) — they were trained on a GPU environment whose
pinned software is not part of this deposit. Those are the **frozen input atom**.

## Environment

Any Python **3.11+** environment works; 3.10 does **not**. `requirements-lock.txt` at the repo root
is the pinned runtime closure (numpy 2.4.4, pandas 2.3.3, scipy 1.17.1, statsmodels 0.14.6,
arch 8.0.0, fredapi 0.5.2, pyarrow 24.0.0, matplotlib 3.10.9, pytest 9.0.3, plus transitive
dependencies), and three of those pins — `numpy==2.4.4`, `scipy==1.17.1` and the transitive
`contourpy==1.3.3` — declare `Requires-Python >=3.11`, so `pip install -r requirements-lock.txt`
fails outright on 3.10. The floor is also recorded as `requires-python = ">=3.11"` in
`pyproject.toml`.
The differential gate additionally needs `pip install selection-fragility==1.0.3` (not part of this
closure). The frozen legacy neural scoreboard `results/extension_scoreboard_1988-2025.csv` has
SHA-256 prefix `abe545a5fdb66132`.

## Run it

```bash
VENV=python3   # or the path to whichever interpreter has this repo's deps installed
$VENV reproduce.py --list     # manifest only (frozen atom + the regenerated pipeline), runs nothing
$VENV reproduce.py --fast     # fast + medium stages only (skip the slow 51-state / population sweeps)
$VENV reproduce.py            # full pipeline; several hours (see FREEZE.md for two timed runs)
$VENV code/instrument/test_fragility.py   # the k* object's own unit tests (greedy == brute force)
$VENV -m pytest tests/
```
`reproduce.py` runs each stage, checks exit code + that the named output CSV was **freshly
rewritten**, and prints a PASS / FAIL / time table. A FAIL means a stage no longer regenerates —
that is the signal to investigate.

Two things are **not** `reproduce.py` stages and have to be run by hand after it:

```bash
$VENV code/pipeline/make_figures.py       # rebuilds all 13 artifacts in paper/figures/ (5 tables, 8 PNGs)
$VENV code/gates/claims.py                # manuscript prose vs canonical.json (ORPHAN / MISPLACED)
$VENV code/gates/metric_consistency.py    # cross-metric consistency of the emitted values
$VENV code/gates/differential_test.py     # frozen code/instrument/ vs the released package
```
`reproduce.py`'s four gate stages are the canonical merge, the canonical `--check` re-derivation,
`selftest_canonical.py` and `acceptance.py`; the three above run outside it and are the remaining
gates whose results `FREEZE.md` records. `differential_test.py` additionally needs
`pip install selection-fragility==1.0.3`, which is outside `requirements-lock.txt` (see
"Environment" above). `make_figures.py` reads only committed result CSVs and `canonical.json`, so it
is safe to run at any point after the canonical merge.

A large, one-time data fetch is triggered by both `--fast` and a full run: `m4_submissions_audit.py`
(tier "med", so `--fast` includes it) downloads the real M4 competition's ~61 archived submission
files from GitHub on first run — `multiseries/data/m4_sub/` is **2.2 GB** once fetched, and the
script needs `unar` (The Unarchiver), NOT `unrar`, installed (`brew install unar` on macOS,
`apt-get install -y unar` on Linux). Once fetched, the data is reused, so this cost is paid once —
but a first-time `--fast` run should be expected to take substantially longer and use substantially
more disk than the stage list alone would suggest, and it will fail outright without `unar` on the
PATH. This stage is macOS/Linux-only: `unar` has no documented Windows install path here, and
`m4_margins.py` (the next stage) reads its output, so a Windows run without `unar` leaves the
M4-champion-flip exhibit and its dependent margins table silently missing.

### Regenerating the curated panel (NOT a `reproduce.py` stage)

`reproduce.py` never rewrites the panel. To regenerate it from the frozen ALFRED vintage caches:

```
<VENV> code/pipeline/run_multiseries.py BOPGEXP BOPGIMP BUSINV DGORDER HOUST M2SL PAYEMS PCE PI RSAFS TCU UNEMPLOY
<VENV> code/pipeline/run_multiseries.py --combine        # expect the "from 12 series parts" scope line
cp multiseries/results/multiseries_predictions.csv multiseries/results/breadth_distinct/breadth_distinct_predictions.csv
shasum -a 256 multiseries/results/breadth_distinct/breadth_distinct_predictions.csv
```
Pass the 12 series names explicitly (a bare run globs every `*_alfred_vintages.parquet`, including
the 51-state archive and non-curated series). Expected: 26,544 rows, 12 series × 6 models,
evaluation years 1990–2025 (first origin per series bounded by ALFRED vintage availability, e.g.
DGORDER 1999, BUSINV 1996); the result is byte-identical to the shipped file (sha256 above; UNEMPLOY
reproduces exactly despite its permanent Oct-2025 absence — `walkforward.realized()`'s calendar-gap
guard is scoped to the months `year_scales()` consumes). A fit that exceeds `MS_FIT_TIMEOUT`
(default 25 s) inside the SARIMA order search is skipped silently, so the panel is in principle
load-sensitive; measured headroom is 16–35×. Then launch `reproduce.py`; never swap the panel
mid-run.

## Determinism

Every stochastic stage is seeded: the block-bootstrap MCS (`mcs_test.mcs`, seed=0),
`winner_stability`, the crowding nulls, and the sims. `reproduce.py` launches sub-scripts with the
*same* interpreter, so there is no environment drift. Seeding fixes the draw stream only *within* a
numpy version: `numpy.random.Generator`'s distribution methods carry an explicit
no-compatibility-guarantee across numpy versions (NEP 19), so pin the numpy version in any
environment where exact bit-for-bit reproduction (not just substantive agreement) matters. Measured
headroom: the curated MCS verdicts survive an entirely fresh stream with ≥67 draws of 2000 to spare
on every series, so this is a low-risk exposure in practice. The non-identification spine is
additionally shown **invariant to the bootstrap tuning**: curated 11/12 is exactly stable across
block ∈ {1,2,3,4,6} × B ∈ {2k,5k} × α ∈ {0.05,0.10,0.25} × 10 seeds each (30 cells, 300 grid
evaluations, 3,600 MCS calls total), cross-checked against the vetted `arch` MCS; a separate
50-seed band is swept at the paper's own default configuration only (block=3, B=2000, α=0.10);
FRED-MD is 54-58/74 across block/B/seed, monotone in α.

## Two platform caveats

1. `code/pipeline/models_freq.py`'s `SARIMA`/`DHR` classes wrap every fit in a 25-second `SIGALRM`
   wall-clock timeout (`MS_FIT_TIMEOUT`, default 25s), used both for the AIC order-selection grid
   and per-window refits. A candidate order or refit that would converge on a fast/idle machine but
   overruns 25s on a slower/loaded one silently falls back to flat persistence instead. Measured
   headroom on the curated panel is 16–35×.
2. On **Windows**, the timeout guard is unconditionally disabled (`signal.SIGALRM` does not exist
   there), so a fit that would time out and fall back to flat persistence on macOS/Linux instead
   runs to completion on Windows — a genuinely different fitted model, hence potentially a different
   forecast/loss/MCS verdict for that series, from identical code/data/seed. This repository has not
   been run end-to-end on Windows; treat the M4/model-fitting stages as macOS/Linux-only.

## Provenance

There is currently no automated hash-check that verifies the frozen atom before a run —
`reproduce.py` only checks per-stage output freshness (mtime), not a content hash of the inputs
above. Today, the frozen atom's protection is: it is git-tracked (so any change is a visible diff)
and no current pipeline stage writes to it. Deleting the FRED/ALFRED/HuggingFace caches does not
just re-pull the same data: FRED and ALFRED continue to publish new vintages and revisions over
time, so a fresh pull today returns different point-in-time data than the one these results were
computed from — which is exactly why these caches are git-tracked rather than left to "just
re-fetch." The Hugging Face Open LLM Leaderboard snapshot has the same property: it is a
point-in-time capture of a leaderboard that keeps changing.

## Per-stage logs

Every `reproduce.py` run writes each stage's full stdout/stderr to
`logs/reproduce_<stamp>/NN_<script>.log` (gitignored). The console summary table shows only
PASS/FAIL and timing; merge CLASH lines, `--check` MISMATCH lists, acceptance DIFFER lists and
producer fallback tallies are in those files.

## The regenerated pipeline (downstream of the frozen atom)

The chain below is a narrative thread, not the full stage list; `reproduce.py --list` is the
authoritative list with tiers and outputs.

`k*` unit tests → per-series MCS (11/12) → social-choice/election reframe → best-arm →
shape-not-magnitude → flagship k*/MCS → M4 audit + density → arena crowding (M4+LLM) → ML witness →
MCS power → real-time Sahm/FOMC-threshold → FRED-MD sweep → MCS/k* robustness grid → state-EB decision →
dMCS. Full list + outputs: `reproduce.py --list`.
